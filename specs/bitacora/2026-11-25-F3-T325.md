# F3 · T325 · Información de versión de este juego

- Fecha: 2026-11-25 · rama `coop/T325` · agente Sonnet bajo el orquestador (ADR-006)
- Ficheros: `runtime/online_version.c`, `runtime/online_version.h`, `tests/test_online_version.c`, y la línea del bucle
  "Pure modules" de `.github/workflows/coop.yml` (`version` añadido a `ratelimit invite netstat`).

## Qué hace

Módulo puro (sin ficheros, sin llamadas al juego, sin sockets):

- `OnlineBuildInfo`: `protocol`, `overlay`, `dlc` (+3 bytes de relleno a cero), `coop[16]`, `gamelib[24]`, `game[16]`.
  Cadenas con terminador dentro del array y ceros después.
- `online_build_init(const OnlineBuildSources*)`: guarda una vez las fuentes (la primera llamada gana hasta
  `online_build_reset`). `online_build_info(out)` copia lo guardado más `ONLINE_COOP_VERSION` ("coop-1"); sin init rellena solo la
  versión cooperativa y deja DLC desconocido (255). No lee disco ni bloquea.
- `online_build_compare(mio, suyo)`: 0 o el motivo del primer campo distinto, en el orden de T314: protocolo → modo
  cooperativo → compilación (`gamelib`) → versión del juego → overlay → DLC. Una cadena sin terminador cuenta como distinta
  (también comparada consigo misma). `game` vacío en cualquiera de los dos lados **no se compara** (T307: `--server` no tiene juego).
- `online_build_valid(b)`: terminadores, DLC conocido (0..7 o 255) y relleno a cero: lo que debe comprobar el receptor.
- `online_build_digest(b, out[16])`: dos carriles FNV-1a de 64 bits, campo a campo (ignora relleno y bytes tras el terminador).
  No es un hash de seguridad; solo distingue compilaciones en el paquete de LAN.
- `online_build_reason_name(motivo)` para registros.

## Decisiones y huecos (para el orquestador)

1. **T308 aún no está**, así que `OnlineBuildInfo` la defino yo aquí. Cuando T308 fije el cable, solo cambia la copia entre
   su estructura y esta; las reglas de comparación no. Si T308 quiere otro tamaño de campo, se cambian las tres constantes `_CAP`.
2. **Las fuentes no se leen aquí.** El verify compila solo `online_version.c`, así que no puede enlazar `gamelib.c` ni
   `dlc_check.c`. Quien integre (T314/T337) llama una vez, al hospedar o unirse:
   `OnlineBuildSources s = { PROTOCOL, gamelib_id(), g_game_version, <N de online_mod/vN>, (uint8_t)rt_dlc_check(root).state };`
   `online_build_init(&s);`. El N del overlay hoy es un literal en `runtime/main.c:507` (`online_mod/v43`) y en
   `tools/online_mod.py:66`; sin constante compartida. [sin verificar si T314 prefiere exponerla]
3. **Regla de compilación (T307)**: uso `gamelib_id()` tal cual. T307 avisa de que `GAMELIB_ID` difiere entre Windows y
   Linux (`GENFLAGS`) y entre CPU normal y compatible; por tanto dos jugadores en distinto SO serán rechazados. Si el dueño
   quiere permitirlo hace falta un id nuevo calculado solo de fuentes (propuesta de T307, no decidida). No lo decido aquí.
4. DLC: se compara el estado (`RtDlcState`) exacto. Dos PC con DLC "listo" coinciden; "listo" frente a "ninguno" no.
   T307 sugería solo *avisar* para el DLC y R3-15 pide rechazar: queda a lo que decida T314.
5. `ONLINE_COOP_VERSION` = "coop-1": valor inicial mío; hay que subirlo cuando cambie algo del modo que no sea cable.
6. No se incluye plataforma ni build id del `main` (T307 los menciona como opcionales).

## Qué debe ejecutar el orquestador

No hace falta Docker para esta tarea. Orden del verify (en la raíz, con `/c/msys64/ucrt64/bin` primero en `PATH`):

```
clang -Wall -Iruntime tests/test_online_version.c runtime/online_version.c -o build/test_online_version && build/test_online_version
```

Esperado: `online_version: OK`, código 0. Después, la CI "Coop tests" ejecuta la misma prueba en Linux (paso "Pure modules").
Opcional en Docker/Linux: la misma orden con `-fsanitize=address,undefined`.
